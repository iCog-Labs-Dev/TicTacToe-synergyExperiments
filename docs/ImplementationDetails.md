# Tic-Tac-Toe Experiment: Integration of PLN, Pattern Miner, and MOSES

## Overview

The Tic-Tac-Toe experiment was designed as a foundational use case to explore and implement the integration between three core components: **PLN (Probabilistic Logic Networks)**, **Pattern Miner**, and **MOSES (Meta-Optimizing Semantic Evolutionary Search)**. The primary goal was to understand how these components can synergistically assist one another in a practical learning environment.

---

## Memory Architecture

To support the integration, a robust memory system was required. We implemented a multi-tiered memory structure shared across all components, categorized into three distinct types:

### 1. Perception Memory

Perception memory serves as a repository for raw observations. While currently a proof of concept and not yet optimized for efficiency, it stores the complete game history, including sequences of moves and their final outcomes.

- **Data Structure**: Each entry is assigned unique game and move IDs.
- **Format**: Observations are stored as implications, such as `(Implication Board1 Board2)`, where `Board1` and `Board2` represent the state of the board before and after a move.
- **Representation**: A board state is expressed as `(Board (X E E O E E E E E))`, where `X` and `O` denote players and `E` indicates an empty cell. For example, a board after move 2 might be represented in this format.

### 2. Beliefs Memory

The beliefs memory is where active learning occurs. Unlike the perception memory, which acts as a simple log, the beliefs memory incorporates frequency information and is designed to remain unique to avoid redundancy.

- **Uniqueness**: Each entry is stored only once to prevent "duplicate reasoning" and the propagation of a false sense of confidence (avoiding counting the same belief multiple times).
- **Format**: Beliefs are perception elements annotated with a **Simple Truth Value (STV)** and a unique index.
  - *Example*: `(Sentence ((Implication Board1 Board2) (stv 0.5 0.3)) (1))`
- **STV Calculation**:
  - **Strength**: Calculated based on a simple probability: how often a specific belief occurs relative to the total perceptions gathered.
  - **Confidence**: Reflects the reliability of the information. We introduced a **Skepticism (K)** hyperparameter, which controls how many datasets the model must observe before increasing confidence. A higher `K` value requires more observations, while a lower `K` allows for faster confidence gains. The overall formula is derived from the PLN framework and NARS implementations.

### 3. Permanent Beliefs

Permanent beliefs consist of background knowledge provided to the learner to facilitate better initial reasoning.

- **Purpose**: These beliefs serve as a starting point, such as the rule that if a move results in a win, the preceding move is responsible.
- **Pattern Integration**: This is also the intended storage location for patterns generated by the **Pattern Miner**, helping the reasoner predict optimal moves.
- **Scope**: While titled "permanent," the main distinction is that these beliefs exist *before* the model begins learning from new observations. Currently, we use a single starter permanent belief to maintain reasoning speed and prevent the PLN from exploring an excessive number of possibilities.

## Data Persistence and State Management

To ensure that learned information is preserved across different game sessions, we implemented a persistence layer:

- **Implementation**: We used Python bindings to write beliefs and perceptions to files. These are loaded into the workspace at the start of each game.
- **Update Cycle**: After each game, beliefs and counts are updated and saved back to the file system.
- **State Tracking**: A dedicated file, `state.metta`, tracks the total number of games played and the total number of beliefs.
- **Status**: While not optimized for scaling or high efficiency, this solution effectively supports our current focus on practical understanding and component verification.

## The PLN Component: The Game Driver

PLN acts as the primary driver for gameplay. It manages move selection through a sequential synergy with MOSES.

### Move Selection Logic

When it is the learner's turn, the `move` function executes the following prioritized search:

1. **Winning Move**: PLN first attempts to find a move that leads directly to a victory.
2. **Draw Move**: If no winning move is found, it seeks a move that secures a draw.
3. **Frequent Move**: As a final resort, it attempts to find the most frequent move for the current board configuration.
   - *Note*: This third step makes the PLN sensitive to the opponent's quality; if the opponent makes many errors, the PLN may learn those sub-optimal moves. However, this exploration is necessary for pattern recognition.

### Key Modifications to PLN

To optimize the reasoner for Tic-Tac-Toe, we introduced three significant modifications:

- **Priority-Based Querying**: Instead of starting queries from the knowledge with the highest confidence globally, we prioritize knowledge that matches the specific structure of the current query. This prevents the reasoner from getting lost in a vast search space.
- **Thompson Sampling**: We replaced "max confidence" selection with Thompson sampling. This technique balances **exploration** and **exploitation** based on the STV of each move, ensuring the model tries different plans rather than repeating the same high-confidence move every time.
- **Backward Chainer Implementation**: The original forward-chaining process was undirected and prohibitively slow. We implemented an **adapted backward chainer** that starts from the query and works backward until a result is found or the depth limit is reached. This change significantly increased the speed of move prediction.

## The MOSES (GP) Component: Strategy Evolution

When PLN is unable to find a suitable move (i.e., it is "stuck" due to lack of experience), the system delegates move generation to **MOSES** (Genetic Programming).

### Evolutionary Strategy

MOSES evolves game policies that generate moves not yet present in the memory.

- **Game Actions**: A policy consists of prioritized actions:
  - Play corner (prioritized by index).
  - Play side.
  - Play center.
  - Play for win (identifying two-in-a-row for the player).
  - Play for block (identifying two-in-a-row for the opponent).
- **Policy Implementation**: The evolved policy provides a prioritized check of these actions. While it may not yet generate a "no-loss" policy, it provides a functional bridge for the PLN.
- **Fallback**: If the policy fails to generate a valid move, the system defaults to random moves (Python version) or forfeits (MOSES version).

### Fitness Scoring

Strategies are evaluated against different opponents:

- **Python Version**: Strategies play 5 times against a random player, then against a minimax player with increasing difficulty (depth 1 to 4). This resulted in more robust, generalized strategies.
- **MOSES Version**: Strategies play against a specific policy (random or minimax) and are scored by win count.
- **Refinement**: We moved away from ranking strategies against each other (which led to local optima) and toward specific feedback-based scoring to ensure the evolution learns effective policies.

### Synergy Output

Once a policy is generated, it simulates a move from the current board state. This move is returned to the MeTTa workspace with default STV values (Strength: 0.5, Confidence: 0.3). If the move proves successful in future games, its STV is adjusted upward; otherwise, it is lowered.

## Pattern Miner: Identifying Logical Structures

The Pattern Miner is the final component in the integration.

- **State Representation**: To simplify reasoning for the miner, we used a concatenated symbol representation of the board state instead of complex expressions.
- **Training**: We tested the miner using a mock dataset of 1,000 games. It successfully identified frequent patterns, such as the logic of placing an `X` adjacent to another `X`.
- **Current Status**: Integrating Pattern Miner directly with PLN has not yet yielded significant performance increases, primarily due to the large amount of history required for effective mining. We intend to continue testing this synergy with larger datasets.

---

## Future Outlook

By iterating through this process, the system collectively builds a belief system of effective gameplay. Over time, STV values converge, identifying moves that are consistently successful across various scenarios and rendering bad moves obsolete. This synergy between PLN's logical reasoning, MOSES's evolutionary exploration, and Pattern Miner's discovery capabilities forms the core of our integrated learning approach.
